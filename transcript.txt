Here is the architectural plan, concurrency strategy, and implementation approach for building the **Coupon Redemption Service**.

---

### 1. Core Concurrency & Correctness Strategy

Because the service must run reliably across **multiple app processes** against a shared database, **in-memory locks (like JS mutexes or semaphores) cannot be used**. All locking and guarantees must be enforced at the database transaction layer.

#### A. Slot Allocation & Global Limit (`max_redemptions`)
* **Strategy:** Use database transactions with pessimistic row locking (`SELECT ... FOR UPDATE`) on the coupon record.
* **Why:** When multiple requests hit either instance simultaneously for the same coupon code:
  1. Transaction begins (`BEGIN`).
  2. Query `SELECT * FROM coupons WHERE code = ? FOR UPDATE;` locks that specific coupon row.
  3. Validate conditions inside the lock:
     - Does coupon exist? (If not $\rightarrow$ `UNKNOWN_CODE`)
     - Is `NOW() >= expires_at`? (If expired $\rightarrow$ `COUPON_EXPIRED`)
     - Is `redeemed_count >= max_redemptions`? (If full $\rightarrow$ `NO_REDEMPTIONS_LEFT`)
  4. Perform customer-level check (for `STANDARD` coupons).
  5. Increment `redeemed_count = redeemed_count + 1`.
  6. Insert into `redemptions` table.
  7. Commit (`COMMIT`).
* **Guarantee:** Strict serialization per coupon row. At no point can `redeemed_count` exceed `max_redemptions`, even under high concurrency bursts across multiple processes. Additionally, a MySQL `CHECK (redeemed_count <= max_redemptions)` constraint will act as a fail-safe.

#### B. Per-Customer Limit for `STANDARD` Coupons
* **Rule:** A `STANDARD` coupon can only be redeemed once per `customer_id` ever. `STACKABLE` coupons have no per-customer limit.
* **Strategy:**
  * For `STANDARD` coupons, query within the transaction: `SELECT 1 FROM redemptions WHERE coupon_id = ? AND customer_id = ? AND status = 'ACTIVE' FOR UPDATE;`.
  * If a record exists $\rightarrow$ reject with `ALREADY_REDEEMED_BY_CUSTOMER`.

#### C. Atomic Expiry (`expires_at`)
* **Rule:** A coupon redeemed after `expires_at` must be rejected; in-flight redemptions at the exact instant must resolve deterministically.
* **Strategy:** Use the database engine's timestamp `NOW(3)` (millisecond precision) inside the transaction query:
  `WHERE code = ? AND expires_at > NOW(3)` or compare against `CURRENT_TIMESTAMP` within the locked row check. This eliminates clock drift between Node.js app instances.

#### D. Cancellation Idempotency (`POST /orders/:order_id/cancel`)
* **Rule:** Reverses redemption, decrements `redeemed_count`. Calling twice must be a no-op the second time, not a double-refund.
* **Strategy:**
  1. Transaction begins.
  2. `SELECT * FROM redemptions WHERE order_id = ? FOR UPDATE;`
  3. If no redemption found $\rightarrow$ `ORDER_NOT_FOUND` (or 404).
  4. If status is already `'CANCELLED'` $\rightarrow$ Return immediately with `{ success: true, message: "Order redemption was already cancelled", already_cancelled: true }` without touching `coupons.redeemed_count`.
  5. If status is `'ACTIVE'`:
     - Update redemption status to `'CANCELLED'`.
     - Update coupon: `UPDATE coupons SET redeemed_count = redeemed_count - 1 WHERE id = ?`.
  6. Commit transaction.

#### E. Idempotency Key Handling (`Idempotency-Key` header)
* **Rule:** Retrying the same redemption request must not double-redeem or charge twice.
* **Strategy:**
  * Dedicated `idempotency_keys` table:
    * `key`: Primary Key (string)
    * `request_hash`: SHA256 of `{ code, customer_id, order_id }` to detect parameter mismatches
    * `status`: `'IN_PROGRESS'` | `'COMPLETED'`
    * `response_status`: HTTP status code (e.g. 200, 409)
    * `response_body`: JSON payload
  * On incoming `POST /redeem`:
    * Attempt `INSERT INTO idempotency_keys (key, request_hash, status) VALUES (...)`:
      * If duplicate key error: Fetch the existing record. If `'COMPLETED'`, return the cached status & body with a header `X-Idempotent-Replay: true`. If `'IN_PROGRESS'`, return `409 Conflict / 425 Too Early` (in-flight retry).
    * If insert succeeds: proceed with redemption transaction and update the record to `'COMPLETED'` with response data upon commit.

### 2. Database Schema (Pure MySQL)

No ORM or framework auto-generation. Handcrafted DDL in `schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS coupons (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(64) NOT NULL UNIQUE,
    max_redemptions INT UNSIGNED NOT NULL,
    redeemed_count INT UNSIGNED NOT NULL DEFAULT 0,
    discount_percent TINYINT UNSIGNED NOT NULL,
    expires_at DATETIME(3) NOT NULL,
    type ENUM('STANDARD', 'STACKABLE') NOT NULL,
    created_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3),
    updated_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    CONSTRAINT chk_redeemed_count CHECK (redeemed_count <= max_redemptions)
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS redemptions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    coupon_id BIGINT NOT NULL,
    customer_id VARCHAR(64) NOT NULL,
    order_id VARCHAR(64) NOT NULL,
    status ENUM('ACTIVE', 'CANCELLED') NOT NULL DEFAULT 'ACTIVE',
    created_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3),
    updated_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    CONSTRAINT fk_redemptions_coupon FOREIGN KEY (coupon_id) REFERENCES coupons(id),
    INDEX idx_coupon_customer_status (coupon_id, customer_id, status),
    INDEX idx_order_id (order_id)
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS idempotency_keys (
    idempotency_key VARCHAR(128) PRIMARY KEY,
    request_hash VARCHAR(64) NOT NULL,
    status ENUM('IN_PROGRESS', 'COMPLETED') NOT NULL DEFAULT 'IN_PROGRESS',
    response_status INT NULL,
    response_body JSON NULL,
    created_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3)
) ENGINE=InnoDB;
```

### 3. API Endpoints & Validations (express-validator)

1. **`POST /coupons`**
   - Validations: `code` (string, trimmed, alphanumeric), `max_redemptions` (int $\ge 1$), `discount_percent` (int between 1 and 100), `expires_at` (ISO8601 future date), `type` (`STANDARD` or `STACKABLE`).
   - Response: `201 Created` with coupon details.

2. **`POST /redeem`**
   - Header: `Idempotency-Key` (required string, UUID/string).
   - Validations: `code` (non-empty string), `customer_id` (non-empty string), `order_id` (non-empty string).
   - Responses:
     - `200 OK`: `{ success: true, remaining: X, redeemed_count: Y }`
     - `404 Not Found`: `{ error: "UNKNOWN_COUPON", message: "Coupon code does not exist" }`
     - `410 Gone`: `{ error: "COUPON_EXPIRED", message: "Coupon has expired" }`
     - `409 Conflict`: `{ error: "MAX_REDEMPTIONS_REACHED", message: "Coupon has reached its maximum redemptions" }`
     - `409 Conflict`: `{ error: "ALREADY_REDEEMED_BY_CUSTOMER", message: "STANDARD coupon already redeemed by this customer" }`
     - `409 Conflict`: `{ error: "ORDER_ALREADY_REDEEMED", message: "Order ID has already been used for redemption" }`

3. **`POST /orders/:order_id/cancel`**
   - Validations: `order_id` (param, non-empty string).
   - Responses:
     - `200 OK`: `{ success: true, message: "Redemption reversed", slot_returned: true }`
     - `200 OK`: `{ success: true, message: "Order was already cancelled", slot_returned: false }` (Idempotent repeat)
     - `404 Not Found`: `{ error: "ORDER_NOT_FOUND", message: "No active redemption found for this order" }`

4. **`GET /coupons/:code`**
   - Direct consistent query against MySQL: `{ redeemed_count, remaining: (max_redemptions - redeemed_count), max_redemptions }`.
